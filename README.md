# RefineTale

> 必要な挙動だけを、既存の設計を崩さずに実装するためのCodex Skillです。

RefineTaleは、コードの追加・修正・リファクタリング・実装レビューをCodexに依頼するときに使います。

Codexは、今回変える挙動と今までどおり保つ挙動を先に整理します。そのうえで、既存コード、標準ライブラリ、プラットフォームの標準機能を優先し、結果が本当に異なる部分だけを実装します。

目標は、単にコードを短くすることではありません。認証、入力の検証、データ保護、互換性、アクセシビリティなどの必要な境界は保ちながら、状態、分岐、データ経路、内部表現、将来用の設定をむやみに増やさないことを重視します。

## まず試す

Codexに次のように依頼して、GitHubリポジトリからインストールします。

```text
$skill-installer install https://github.com/alka0000-dev/codex-skill-refinetale
```

インストール後にスキルが表示されない場合は、Codexを再起動してください。

コード作業の依頼の先頭に`$refinetale`を付けます。

```text
$refinetale この機能を、既存の挙動を維持しながら実装してください。
```

過剰実装がないか確認するレビューにも使えます。

```text
$refinetale この差分に、不要な分岐、重複した状態、先行実装がないかレビューしてください。
```

## 使うかどうかの目安

次のような悩みがある作業に向いています。

- 大きめの機能を頼むと、依頼していないAPI、設定、画面まで増えてしまう
- 同じ意味の状態や変数が複数あり、どれが正しい値なのか分かりにくい
- 既存機能と新機能で、ほぼ同じ処理が別々に作られてしまう
- 一時対応や将来用のコードが、そのまま残り続けてしまう
- 実装は必要最小限にしたいが、認証、入力の検証、互換性までは削ってほしくない
- 完了報告と、実際に確認できた内容を対応づけてほしい

一方、一般的な技術説明、コードを扱わない文章作成、脆弱性の発見自体を目的とするセキュリティ監査には使いません。セキュリティに関係する通常の機能追加や修正では、認証などの必要な境界を保つために利用できます。

## RefineTaleがすること

| 確認すること | 実装への反映 |
| --- | --- |
| 今回の依頼 | 変える挙動と、今までどおり保つ挙動を分ける |
| 既存の実装 | 再利用できるコード、型、標準機能、導入済みの仕組みを探す |
| 状態とデータ | 同じ意味の値を重ねて持たず、正本となる管理場所を一つにする |
| 共通点と違い | 共通する挙動は共有し、結果が異なる場所だけを分ける |
| 安全性 | 認証、入力の検証、データ保護、互換性、アクセシビリティを維持する |
| 完成条件 | 依頼された挙動と必要な確認を満たしたら、周辺機能を足さずに終了する |
| 完了報告 | 変えた挙動と保った挙動を、それぞれ確認方法と結果に対応づける |

## Ponytailとの関係

RefineTaleは、[Ponytail](https://github.com/DietrichGebert/ponytail)の考え方を参考にし、自分の用途に合わせて再設計・拡張したSkillです。

出発点にしたのは、Ponytailが重視する次の考え方です。

- 依頼に必要のないものまで実装しない
- 新しく書く前に、既存コードを再利用できないか確認する
- 独自実装や新しい依存関係より、標準ライブラリやネイティブ機能を優先する
- 少ない実装を理由に、入力検証、エラー処理、セキュリティ、アクセシビリティを削らない

RefineTaleでは、その出発点に次の規則を加え、実装前の整理と完了時の検証を強くしています。

- 「変更する挙動」と「変更しない挙動」を変更契約として分ける
- 状態、変数、データ経路の正本を一つにし、同じ意味の値を重複して管理しない
- 共通する挙動と、結果が異なる挙動を分け、差分がある場所だけを分岐させる
- 変更した挙動と保った挙動を証拠に対応づけ、証拠が揃わない状態で完了したとは報告しない

このため、RefineTaleはPonytailをそのまま再配布したものではなく、最小実装という出発点を共有しながら、変更範囲、データの所有権、実装経路、完了条件を明示する方向へ設計を広げています。

## 使い方

実装方法を細かく指定しなくても、Codexが依頼内容と既存コードを確認します。希望する実装方法や完成形がある場合は、その内容も一緒に伝えてください。

次の3点が分かると、変更範囲を判断しやすくなります。

- 何を変えたいか
- 何を今までどおり保ちたいか
- どの状態になれば完成か

すべてを決めておく必要はありません。分かる範囲だけでも、次のように伝えられます。

```text
$refinetale
変更したいこと: （追加・修正したい挙動）
保ちたいこと: （変えたくない既存の挙動）
完成条件: （確認できれば完了と判断できること）
```

## 完了時に確認できること

コードの変更、具体的な実装案、実装レビューを依頼した場合、RefineTaleの`SKILL.md`はCodexに次の内容を最終回答へ含めるよう求めます。

- 今回変えると決めた挙動
- 今までどおり保つと決めた挙動
- 各挙動を確認した方法と結果
- 確認を実行できなかった場合は、その理由、確認に必要な最小限のテスト、期待する結果

必要な証拠が揃っていなければ、完了したとは報告しません。これは、実行できなかった確認まで成功したとみなす保証ではなく、確認できたことと確認できなかったことを分けて報告するための規則です。

## 比較評価の結果

2026年9月2日に、1つの公開リポジトリの固定コミットへ6種類のフロントエンド機能を追加する比較評価を行いました。各機能をRefineTaleなし・ありで3回ずつ実装し、合計36回の結果を比較しています。

両条件とも18回すべてがフロントエンドのビルドと課題ごとの完成条件を満たしました。その範囲で、追加されたソースコード行数の合計は4,118行から1,777行へ減り、削減率は56.9%でした。課題ごとの中央値を同じ重みで平均した削減率は44.9%です。

```text
追加されたソースコード行数（18回の合計）

RefineTaleなし  ████████████████████  4,118行
RefineTaleあり  █████████               1,777行
```

| 確認項目 | RefineTaleなし | RefineTaleあり |
| --- | ---: | ---: |
| ビルドと完成条件を満たした実装 | 18/18 | 18/18 |
| 追加されたソースコード行数 | 4,118行 | 1,777行 |
| 1回あたりの平均追加行数 | 228.8行 | 98.7行 |
| 完成度、設計との整合、実装範囲、実装経路の匿名採点 | 87.5% | 98.6% |
| 重大な失敗 | 0件 | 0件 |

日付選択、ファイル選択、複数ステップのフォームでは、依頼されていないAPI、独自の状態管理、追加画面などを抑える差が見られました。

一方、RefineTaleありでは、平均実行時間が26.9%、回答の出力トークン数が31.1%増えました。短い回答や速い実行を得るためのSkillではありません。変更後に保守するコードと、把握し続ける必要がある実装上の決まりを増やさないことが目的です。

### この結果からは分からないこと

56.9%は、この評価に含まれる36回の追加行数を合計して比較した記述統計です。RefineTaleを使えば、別の作業でも同じ割合でコードが減ることを示す数値ではありません。

- 対象は、1つの公開リポジトリに追加した6種類のフロントエンド機能です
- 課題はPonytailの公開ベンチマークをもとにしていますが、選択、実行、採点、監査はRefineTaleの作者が行っており、第三者評価ではありません
- 同じモデルと推論強度を使い、各条件を3回ずつ実行しました。反復実行を独立標本とみなした有意差検定は行っていません
- ビルドと課題ごとの完成条件は確認しましたが、ブラウザ操作、見た目、自動E2Eテストは評価していません
- バックエンド機能、ほかの言語やリポジトリ、長期的な保守性、実運用で同じ結果が得られるとは限りません
